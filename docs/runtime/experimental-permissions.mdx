title: Experimental permissions and diagnostics
description: Process-wide resource policy for trusted application code.

The permission model is opt-in. Without `--experimental-permissions`, Bun remains unrestricted and `process.permission.has()` reports unrestricted access for recognized scopes. This experimental feature constrains trusted application code. It is not an operating-system sandbox for hostile code, native extensions, or a concurrently changing filesystem.

## Policy and grants

`--secure` denies resource access by default. Explicit allow-lists constrain their scope even without `--secure`; omitted scopes otherwise remain unrestricted. Permission flags require `--experimental-permissions`. Whenever any resource scope is restricted, capabilities such as subprocesses and native code also require their explicit grants.

```sh
bun --experimental-permissions --secure --allow-read=./app --allow-net=api.example.com:443 ./app/index.ts
```

The CLI publishes one immutable process-wide policy before loading user modules or preloads. Workers inherit that policy; replacing `execArgv` does not replace it. User entry points, imports, and build inputs require read grants. Built-in modules do not require grants to their internal implementation files.

| Flag                      | Authority                                                                        |
| ------------------------- | -------------------------------------------------------------------------------- |
| `--allow-read=path`       | Read a canonical file or directory subtree                                       |
| `--allow-write=path`      | Modify a canonical file or directory subtree                                     |
| `--allow-net=host[:port]` | Connect, listen, and resolve the named host                                      |
| `--allow-env=NAME`        | Read and mutate a named environment variable                                     |
| `--allow-run`             | Start subprocesses, execute shell commands, and use persistent system scheduling |
| `--allow-worker`          | Start workers under the same process policy                                      |
| `--allow-ffi`             | Load or execute native code, including native addons and SQLite extensions       |
| `--allow-sys`             | Access protected host information and process controls                           |
| `--allow-inspector`       | Start or connect the Inspector                                                   |

Resource lists accept `*` to leave that scope unrestricted. Environment grants may also end in `*` to match a name prefix. Empty or malformed grants are rejected before user code. Native-code and subprocess grants confer broader authority than Bun's resource checks: those programs and libraries can use operating-system APIs directly.

`process.permission.has(scope, resource)` queries the same policy. Resource scopes are `fs.read`, `fs.write`, `net`, and `env`; capability scopes include `run`, `worker`, `ffi`, `sys`, and `inspector`. Capability queries ignore the resource argument. A resource-less query for a restricted resource scope returns false. `has("net", "host")` queries hostname resolution authority; use `has("net", "host:port")` to query the transport port. Local-socket queries test connection authority; a filesystem Unix listener separately needs write authority. A query is diagnostic; an earlier successful query does not reserve access for a later operation.

## Filesystem behavior

Checks resolve symlinks and authorize the actual target. Operations on directory entries authorize the canonical parent and entry; a trailing separator follows the final symlink as the operating system does. File-descriptor operations reauthorize the descriptor's current path. Standard-stream Blob transfers retain stdin read and stdout/stderr write authority; that exception does not grant filesystem metadata access. Read/write opens require both grants. Parent components (`..`), malformed paths, and paths that cannot be safely resolved fail closed.

Hooks cover Node filesystem operations, Blob and Bun file transfers, streams and server file responses, watchers, archive/image operations, glob traversal, module resolution, build inputs/outputs, and CPU/heap profiler output. Recursive operations check visited entries instead of granting an entire traversal from its starting directory. These checks do not eliminate races between pathname authorization and the operating-system operation; use an OS security boundary where another actor can replace paths maliciously.

SQLite uses a permission-aware VFS for database files, journals, WAL and shared-memory sidecars. A database-file grant does not grant its sidecars. Grant the containing directory when those operations are required. Memory databases remain available. Native VFS selection, extensions, custom libraries and native file controls cannot bypass a restricted policy without native authority. Unnamed temporary files fail closed under filesystem restrictions. Restricted SQLite uses checked reads instead of memory mapping; a read-only WAL database can still require sidecar write authority.

On Windows, a restricted network policy also checks filesystem paths before canonicalization. Ordinary local disk paths are supported; direct UNC paths need a matching hostname grant without a port. Following reparse points, mapped drives, SUBST drives, and unknown device mappings is conservatively rejected. Entry metadata and removal can still operate on a link itself; trailing separators request traversal and are checked accordingly. Descriptor checks use the opened name before canonicalization. These Windows paths have separate cross-target compiler coverage; runtime execution still requires a Windows host.

## Network behavior

Host grants are case-insensitive ASCII hostnames or canonical IP addresses, optionally followed by a port. Use punycode for internationalized hostnames and brackets around IPv6 addresses with ports. `*.example.com` matches subdomains at a label boundary. DNS resolution authorizes the hostname; a port on a grant constrains transport, not the DNS query itself.

Fetch authorizes every redirect destination and proxy connection. HTTP, WebSocket, TCP, UDP, DNS and server listeners check their actual endpoint. Node's default DNS-to-connect path carries native authorization tied to the resolved address and port. A custom lookup callback needs a grant for the IP address it returns. Adopting an existing socket descriptor is currently unsupported under a restricted network policy, even when its peer would otherwise be permitted.

Local socket grants use `unix:/absolute/path`, `abstract:name` for Linux abstract sockets, or `pipe:name` for Windows pipes. A filesystem Unix listener also requires write authority for its socket path. A Unix HTTP request checks its socket rather than the synthetic URL hostname.

## Environment and native defaults

Restricted environment objects filter initial reads, enumeration, descriptors and cached properties. Denied reads return `undefined`; denied writes, deletions and definitions throw before the target mutation. JavaScript argument expressions and descriptor getters execute according to ordinary JavaScript evaluation rules. Windows names are case-insensitive. Prototype or reflection operations do not reveal a separate unrestricted backing object.

Native environment consumers, including bundler inlining, server defaults, object-storage credentials and Redis defaults, use the same grants. Explicit application options remain available when their operation is otherwise permitted.

## Reporter output

The Inspector reporter emits an object with `tests` and `diagnostics` arrays. Durations use protocol milliseconds. Console and lifecycle events received with exactly one active test attach to that test; otherwise they remain in `diagnostics` with the active IDs and a reason. The reporter waits for Inspector initialization and collects events through disconnect.

## Development verification

Run from the owning checkout:

```sh
bun install --frozen-lockfile
bun install --frozen-lockfile --cwd test
bun run typecheck:permissions
bun bd test test/cli/permissions.test.ts test/cli/inspect/permission-reporter.test.ts test/js/bun/test/expect-extend-preload.test.ts test/cli/heap-prof.test.ts
bun test test/integration/bun-types/bun-types.test.ts
```

Native validation must use `bun bd` so tests exercise the modified executable. The declaration integration command is the repository's documented exception for type-only validation. `typecheck:permissions` is a focused compiler check of the permission tests, profiler tests, reporter, matcher regression coverage, and imported harness; it does not check the entire repository.

A passing local suite proves its exercised paths on that host. Cross-platform execution and admitted CI jobs require separate evidence; saved workflow configuration alone does not establish either.

The `Permission declarations and lint` GitHub workflow checks focused types, packaged declarations and JavaScript lint using Bun 1.4.4. Native runtime tests remain part of the repository’s Buildkite test pipeline; that GitHub workflow does not build or test the native runtime.
